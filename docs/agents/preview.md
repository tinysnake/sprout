# Human preview protocol

Use this protocol when an Agent is asked to present a working Sprout Web build to a Human for manual review, or to end that review. It is a target workflow and a decision boundary, **not a claim that the repository already has a preview manager**. In particular, the network exception proposed below is unresolved: do not turn this document into a command to serve plaintext Web to other machines.

## Boundary and terms

- A **preview** is one Human-facing, functional Sprout Web plus its Sprout instance and dedicated durable state. It is not a fixture-only page. Hot reload may be used, but the Human sees only one stable entry point.
- Per development host, at most one Human-facing preview may own the entry point at a time. Automated tests may use ephemeral loopback-only servers; they neither occupy that entry point nor touch preview state.
- The preview entry point has one fixed, locally configured port and binds to `0.0.0.0`; it must not silently choose a free port or fall back to loopback. The port value and host/network details belong in ignored local configuration, not tracked files or issue records. A listener binding all interfaces does not by itself restrict access to a private network.
- `.preview-data/` is the ignored, preview-only state root. It contains a **confirmed baseline**, a separate **working copy** for the current review, non-secret local settings, and recovery metadata. The database and the preview-dedicated Project workspaces form one state set: a retention decision applies to both. The host-managed Environment Worker key, engine logins, and operator credential are not part of this set and must not be copied into it.
- The words *preview* and *working copy* describe this development workflow, not Sprout's domain **Environment instance**, **Task context directory**, or **Project workspace**. A preview may contain real Project workspaces and unfinished Tasks, so stopping it does not automatically end or release them.

## Agent procedure

1. **Prepare and identify.** Read this protocol; locate the ignored local preview settings and the confirmed baseline. Check that the required operator credential, enrolled Worker, engine login, and preview workspace are available without reading or recording secret values. Never silently adopt the normal `sprout.db` or an existing non-preview Project workspace as the preview baseline. If no baseline exists, start from an empty preview state and let the Human configure it; it becomes a baseline only through the end-of-preview decision. If the prerequisite manager/settings do not yet exist, report that gap rather than improvising a state copy or startup command.
2. **Resolve ownership before touching a process.** Inspect both the preview ownership record and the fixed port. A still-running preview, a stale or ambiguous record, or any occupied port is a Human decision point: explain what can be verified and ask whether to reuse the existing preview, end it, or leave it alone. Ask explicitly whether to close a running instance or free an occupied port. Only after consent, verify process ownership with OS/process-start evidence, stop the owned instance gracefully, wait for it to exit, and re-check the port. Consent alone does not establish ownership; never terminate an unknown listener. If ownership cannot be proven, ask the Human to resolve it manually and remain blocked. Never start a second preview on another port.
3. **Recover pending state.** If a prior preview crashed, stopped without a retention answer, or was interrupted during promotion, preserve its working copy and ask the Human to resolve that pending review before creating another. Do not promote, delete, or overwrite either state set by default. Record local pending/decision status without secrets or host identifiers.
4. **Stage the review.** Copy the confirmed baseline into a new working copy while the store and associated workspaces are quiescent; do not copy a live SQLite file as though it were a consistent snapshot. Check schema compatibility before serving and migrate only the working copy. A failed migration leaves the baseline intact and the preview unavailable until the Human chooses recovery or a fresh start. Use the same fixed preview entry point for every review; built assets and any development server must route through that one entry point. Check that the actual Web and API load from the Human's intended access path, that sign-in works, and that prerequisite state is usable. Report the verified access path to the Human privately, not in tracked records.
5. **End and decide.** Closing a browser is not an end signal. On an explicit request to end the review, first inspect active Agent runs, Task leases, and recovery work. If any are unresolved, do not promote state or silently release capacity; explain the blocker and ask the Human to resolve it or leave the review pending. Once quiescent, stop the preview gracefully and close the database, then ask the Human whether to **retain** the database and preview Project workspaces together as the next confirmed baseline or **discard** the working copy. Record the explicit decision locally. An unanswered question, an abnormal exit, or a failed replacement leaves the working copy pending. Promote a retained pair through a staged, recoverable replacement that can never expose a database/workspace mismatch as a confirmed baseline; discard only the working copy after explicit choice. Keep the prior baseline until promotion succeeds. Clean up obsolete working copies only after their disposition is known.

At each block, tell the Human which condition failed and what decision or host action is needed. Never substitute an ephemeral port, an empty database, a different workspace, or an insecure network path just to produce a URL. Repository docs and issue records must not contain real preview addresses, port bindings, credentials, session cookies, or personal data. Preview baselines use synthetic or explicitly permitted test data; ignored files still need appropriate local permissions and cleanup.

## Post-merge process freshness

Preview processes **load code at process start**: the API backend and the Worker execute whatever checkout state existed when they launched, while the Vite dev server transforms the current working tree on demand. A green integration gate therefore proves the *committed tree*, never the *running processes* — merging new code does not by itself update what the Human sees. This gap has caused two acceptance failures (a preview page-size knob ignored by an old backend; a missing task-group scope because the task-lifecycle hooks predated the merge).

Rules:

1. **Freshness is part of delivery.** Never tell the Human a preview is ready for acceptance until every code-loading process (backend, Worker) has a start time at or after the newest integrated commit presented for review. Compare `ps -o lstart= -p <pid>` against `git log -1 --format=%ci <head>`; the Vite dev server is exempt because it serves the working tree on demand.
2. **Restart after integration, or record the deferral.** When an integration merge advances past the running processes' code, restart them from the integrated worktree with the recorded preview environment. If an active run or lease forbids a restart, write `pendingRestart: true`, the reason, and the target `codeHead` into the preview ownership record immediately; a settled run executes the pending restart. A deferral without a record is a lost restart.
3. **State the outcome where completion is claimed.** Any completion, hand-off, or acceptance report about integrated work must say explicitly whether the preview was restarted at the new `codeHead` or deferred (with the recorded reason). Omitting this line makes the report incomplete.

## Unresolved security exception (not an approved launch mode)

The requested temporary arrangement would expose the fixed, all-interface preview entry point to other LAN browsers over plaintext HTTP. This conflicts with [ADR-0009](../adr/0009-self-hosted-operation-and-recovery-promises.md): non-loopback Web requires TLS over an operator-managed private network **and** Sprout operator authentication. Plaintext can expose login credentials and browser sessions even when authentication is enabled. [ADR-0012](../adr/0012-production-workers-use-enrollment-backed-outbound-connections.md)'s explicit trusted-private-network plaintext exception is for Worker connections, not Human Web sessions. Local firewall or a trusted LAN does not make this an approved Web mode. This exception remains an open proposal; Agents must not initiate non-loopback plaintext preview under this protocol. A compliant preview requires an approved TLS/private-network entry point while preserving the fixed port and all-interface bind, or a separately approved change to the governing safety policy. Until then, report the preview blocked instead of starting it.

## Implementation gap

Today `npm start` defaults to a loopback-only Sprout instance and a database outside `.preview-data/`; the development server chooses its port from environment settings and has permissive dev-host/CORS configuration. The repository does not yet provide an owned, fixed-entry preview manager, a persistent ownership/decision record, or recoverable baseline-plus-workspace promotion. This document specifies the required behaviour for future tooling and for Agents coordinating with a Human; it does not make those guarantees true by itself. Implement and verify the ownership fence, fixed-port refusal, coherent snapshots/promotions, restart recovery, private-network security, and end-of-preview human choice before presenting the workflow as automated.
