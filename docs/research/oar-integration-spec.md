> Current privacy scope: [ADR-0020](../adr/0020-defer-privacy-hardening-and-redaction.md) defers privacy hardening and content redaction. Issue #226 carries the corresponding acceptance amendment. Authentication, execution authority, recovery, and Sprout-owned interfaces retain their requirements.

## Problem Statement

A Human extending Sprout to another coding-agent engine currently depends on a separate Sprout adapter for each engine's process transport, native protocol, event parsing and session continuation. Maintaining these integrations repeats work already performed by OAR and increases the cost of supporting new engine versions.

The Human also intends to implement #225, which separates host-run engines from authorized remote work Environments. Building new native Claude integration and extensive Pi/Codex control plumbing before choosing the engine substrate risks replacing that work again during OAR adoption. Conversely, migrating all engines to OAR before verifying the controls required by #225 could remove access to mechanisms needed for restricted remote execution.

The Human needs a shared engine integration that reduces vendor-specific maintenance, preserves Sprout's observable execution and recovery behavior, and establishes whether OAR can support #225 before production replacement becomes a commitment.

## Solution

Use `@botiverse/oar` behind one reusable Sprout `OarEngineAdapter`, while retaining a Sprout-owned execution Interface. Native protocol and runtime transport belong to OAR; Agent identity, Project and Task authority, admission, leases, results and recovery remain Sprout responsibilities.

First validate OAR against the decisive engine controls required by #225. Record which controls work, which require a small integration hook or upstream change, and which are not yet established. Do not represent MCP attachment alone as proof of restricted remote execution.

After that decision is evidenced, deliver a minimal production replacement for Codex and Pi in the existing Environment-hosted mode. Register each accepted runtime through a shared runtime catalog and the same Adapter Implementation. An additional runtime supported by that contract should need configuration and acceptance evidence rather than another native protocol parser.

Implement #225 on the selected engine substrate afterward. Broader OAR runtime migration follows the required product path. An unresolved engine control has a bounded recorded remedy or native exception rather than blocking Sprout indefinitely or being silently treated as supported.

35. As a Human, I want the existing host execution policy applied explicitly, so that OAR defaults cannot silently grant broader filesystem access.
36. As a Human, I want session-specific configuration isolated from other active Agents, so that one session's runtime settings do not change another session's behavior.

## Implementation Decisions

- **Execution seam and ownership:** retain the existing Runtime admission/orchestration Interface as the principal application seam. Keep a Sprout-owned `EngineAdapter`/`EngineSession` Interface for the Worker Implementation. Simplify members where actual production callers permit it, but preserve observable admitted-run semantics. Do not make Core, durable product records or the Worker protocol depend directly on OAR Session types, raw records or native control operations.
- **One shared Adapter:** build one reusable `OarEngineAdapter` parameterized by accepted runtime identity, capability metadata and validated host policy. Registered Codex and Pi instances share that Implementation. Do not introduce a Sprout wrapper class for every OAR runtime. Engine-specific differences may use small demonstrated compatibility hooks, not separate vendor transports or general escape hatches.
- **Primary completion scope:** the minimal production replacement requires Codex and Pi in Environment-hosted mode, preserving the existing macOS and Windows operator path. Existing agy and OpenCode support remains available through its accepted Implementation until a corresponding replacement is accepted. Migrating additional runtimes is not required to complete this slice. Claude is a required candidate for the #225 feasibility decision, not a production Host-run capability supplied by this issue.
- **Sequencing and decision gate:** begin with a bounded prototype of the controls needed by #225. Produce a versioned matrix for Pi, Codex and Claude identifying mechanism, evidence level, platform scope and remaining gaps. Only plan production control work whose prerequisite is established. If the proposed OAR route cannot satisfy a necessary control, stop that route and record one bounded remedy: an upstream extension/fix or an explicit native Implementation exception. Do not invent successful remote-work acceptance or make universal OAR coverage a prerequisite of the product.
- **Relationship to #225:** this issue selects and minimally integrates the engine substrate before #225's full Host-run delivery. Startup parsing, durable placement facts and the shared Environment operations Module from #225 may proceed independently once their Interfaces are settled. Do not amend #225's acceptance, close it, or automatically make it depend on completion of unrelated runtime migration. Any eventual tracker dependency must reflect the evidenced chosen route.
- **Feasibility evidence:** evaluate Pi tool-operation replacement or restriction and MCP registration/withdrawal, Claude built-in exclusion and discovery-source control, and Codex native executor binding or an accepted restricted external-tool route. Check local-tool denial, remote origin, session resume, stale binding behavior and no local fallback with controlled fixtures. Source inspection and protocol acceptance are weaker evidence than model-issued execution; report them separately. A missing live installation or authentication prerequisite remains an evidence gap.
- **Shared runtime catalog:** use one catalog to describe product engine ID and label, OAR runtime ID, enabled status, accepted versions/platforms, streaming and instruction capabilities, verified readiness sources, and host execution policy. Selection, admission, readiness and product model selectors consume consistent projections of this catalog. Finding a runtime does not enable or authorize it. Preserve existing product IDs such as `codex` and `pi`; record Implementation/version identity separately where evidence requires it.
- **Environment placement:** during this production slice, engines continue to execute behind the enrolled Environment Worker. Core gains no native process-start rules or direct vendor connection path. OAR runner packaging belongs to the execution host. Introducing Host-run placement, Engine host identity or execution-mode configuration remains #225 work.
- **Runner and supervision:** execute OAR in a separately supervised runner for each Sprout EngineSession so embedded SDK execution, process-global configuration and escalation are isolated from the long-lived Worker. Keep runner communication generic and Sprout-owned; it must not reintroduce vendor JSON-RPC or CLI parsing. Bound startup, cancellation escalation and close. Reuse OAR's native cleanup where it is proven, while retaining host-level escalation for an unresponsive embedded runtime. An ordinary child process is lifecycle isolation, not an OS sandbox.
- **Termination evidence:** supervise the execution tree on each supported platform and observe termination or establish an accepted fence before normal release. Parent exit, accepted cancellation, a reconnect, a timeout or a new runner identity alone cannot establish remote or descendant termination. Preserve unresolved outcomes and leases when proof is insufficient.
- **Configuration and host policy:** apply the selected execution posture before session opening. Preserve the current ordinary-host Codex read-only posture and container full-access posture explicitly. Treat OAR's full-access defaults as dependency behavior, not Human authorization. Configure process-global OAR environment settings only within the corresponding runner; never mutate a shared Worker's environment per concurrent session. Restriction sufficient for the current Environment-hosted path is not evidence of the stronger host read isolation required by #225.
- **Session opening and instructions:** map the Worker-resolved working directory, requested model/effort, instructions and optional resume key into supported OAR options. Prefer verified append-to-system-prompt delivery where appropriate; use an existing verified engine-readable file/hook channel where necessary. Check refused options and read-back where available. Report fallback or unavailable delivery honestly, preserve user-owned files, and do not silently drop instructions or inject them into every user prompt. A runtime without a required delivery mechanism is ineligible for that use.
- **Native session identity:** persist the native Session identity actually observed. Preserve the existing Agent/engine/Environment/working-directory Session-key scope in this mode. Verify whether prior Codex and Pi stores and Session keys are compatible with the replacement, including Pi's configured session directory. If reuse is unsupported, record that fact without merging histories or erasing old records. Implementation migration must not clear unresolved runs or leases.
- **Resume refusal:** preserve the existing neutral classification and fresh-session retry only for an explicit refusal that establishes no work was performed. Generic startup, authentication, provider or transport failures do not discard a valid key or justify retry. An ambiguous refusal remains a failure requiring reconciliation, not a inferred stale key.
- **Run control:** one admitted Sprout Agent run owns one root activation. Use OAR prompt acceptance and correlated observations rather than implicitly queueing a busy prompt. Do not expose OAR `queue`, `deliver`, `steerOrQueue` or subagent spawning as alternate admission paths. Sprout retains ownership of waiting work and Agent wakes. Native spontaneous activity during open or resume must be observed and attributed before new work is considered safe.
- **Event correlation:** correlate observations with execution host/runner identity, session identity, boot identity, admitted run and native request/turn identity where supplied. Subscribe so retained opening observations are not lost. OAR resume creates a new stream at sequence zero; its sequence is not the durable Worker journal acknowledgement identity. Multiple flat events may share one record sequence and must not be discarded as duplicates. Child/background terminal events and stale observations cannot settle or enter another run.
- **Final-answer and outcome translation:** map provider-independent progress into Sprout events and select the final answer using actual native terminal-message evidence and established Sprout fallback behavior. Do not assume OAR's root-text concatenation is the final-answer contract. Failed and interrupted outcomes remain distinct from completed output. Genuinely successful empty output is permitted; an error with empty text is a failure. Where root-turn attribution is not reliable, withhold the affected runtime until fixed or until a verified bounded hook resolves it.
- **Cancellation:** interpret accepted OAR abort as cancellation delivery. Wait for native settlement only within host supervision bounds, then escalate. A late abort racing with a completed turn retains the real completed outcome. Cancellation requests must not fabricate native terminal facts. Integrate settlement and uncertainty with existing Chat interruption and Task-linked stop distinctions rather than redefining Task lifecycle.
- **Usage and valuation:** preserve the most detailed trustworthy per-run usage facts, completeness and source/version provenance. Use native per-turn usage when available; use cumulative deltas only when attribution is verified and concurrent/background usage cannot contaminate the run. Deduplicate reports, avoid double-counting resumed history and child usage, retain partial facts on interrupted/failed work, and never invent zero for missing metrics. Preserve the existing separation of billed cost, API-equivalent estimates, billing basis and valuation provenance. Do not sacrifice measured Codex/Pi usage detail merely to use a coarser common OAR projection.
- **Readiness and authorization:** reuse proven OAR installation/authentication/model queries individually, subject to the existing non-inference contract. Executable presence, account sign-in, model availability and accepted controls are separate facts. Unknown remains unknown; matching explicit Human model authorization remains a distinct evidence source under the existing readiness decision. Probe, reconnect, heartbeat and runtime discovery never prompt a model or export credentials.
- **Recovery and authority:** preserve Task-held leases, run-held leases, enrollment authentication, Worker epochs, revocation, recovery journals and Human-only lifecycle decisions. Worker loss and replacement synchronize retained evidence and fence new work; they do not replay old prompts or prove the old session stopped. Removing an old Adapter is not evidence that its old execution has terminated.
- **Diagnostics and ownership:** project useful bounded progress/results and runtime/SDK/OAR version, failure, and correlation facts through Sprout-owned records. Keep credentials host-local and preserve the EngineAdapter/EngineSession seam; do not directly serialize OAR records as durable product or Worker protocol objects because that couples those contracts to vendor schemas. Privacy hardening, content redaction, and privacy-specific export restrictions are future work under ADR-0020 (`docs/adr/0020-defer-privacy-hardening-and-redaction.md`), not current acceptance or preservation requirements.
- **Dependency and packaging:** pin the OAR version accepted by the prototype and production contract rather than taking a floating upgrade. The inspected candidate is 0.35.0; it is not already accepted. Update declared runtime support and Worker/runner installation and service packaging to Node.js 24+ consistently. Refuse unsupported versions before admitting work with actionable host-local guidance. Honor Apache-2.0 license and attribution requirements if source is copied; prefer dependency use.
- **Replacement and update gate:** old and new implementations may coexist during a bounded acceptance comparison. Once a runtime replacement is accepted, remove its old production Adapter, native transport/parser code and redundant implementation-coupled tests. Retain tests of Sprout's public semantics. Re-run affected shared contracts and live runtime/platform scenarios on OAR or native-runtime upgrades. Resolve common protocol defects upstream rather than accumulating another vendor parser in Sprout.
- **Documentation:** record the shared Adapter ownership and accepted version/capability matrix. Update engine integration and runtime installation guidance and any affected execution/usage decisions without changing Environment placement or #225's mode-specific rules. Use the established reference repositories as design cross-checks and distinguish source facts, prototype outcomes and production acceptance.

## Testing Decisions

- **Primary application seam:** use existing Runtime construction/admission followed by established Message and Task commands. Verify composed Message-to-run-to-projected-reply behavior, durable outcomes, progress, usage, lease effects and recovery with the shared OAR Adapter injected behind existing engine/Worker Interfaces. Avoid a new testing or orchestration Interface solely for OAR.
- **Focused conformance seam:** use the existing `EngineAdapter`/`EngineSession` Interface for cases that need deterministic OAR event sequences or runner faults. Script the external OAR runtime/session dependency instead of recreating vendor parsers. Reuse these scenarios across accepted runtimes and the version-update gate. A generic runner fixture is an Implementation dependency, not an additional public product seam.
- **Good tests:** assert externally visible execution, persisted outcomes and resource effects. Do not test private methods, forwarding callback counts, argv snapshots, catalog array order unrelated to product behavior or internal storage layouts. Favor shared risk-based scenarios over one test per mapping field. A model preferring a remote tool is not proof that local tools are denied.
- **Prior art:** extend composed Runtime collaboration and SQLite integration scenarios, failed-engine settlement and final-reply projection tests, Task-context and retained-lease journeys, explicit resume-refusal behavior, Worker journal/reconnect/epoch/revocation cases, usage deduplication and provenance cases, and current engine lifecycle tests. Existing Pi/Codex probes provide initial evidence only; new adapter acceptance crosses the public engine and application seams.
- **Opening and admission:** cover missing installation, incompatible version, refused instructions/model/effort, explicit no-work resume refusal and unrelated failure on valid resume. Assert truthful failure, bounded startup cleanup, preserved stored keys when appropriate and no implicit busy-prompt queue or post-acceptance engine fallback.
- **Progress and correlation:** cover retained opening notifications, multiple facts sharing a record sequence, resumed sequence reset, child/background turn endings and late events from an old runner. Assert that only the correct root run settles, every permitted progress fact appears once, and failures never project a completed reply. Include a regression scenario representing the upstream Claude attribution race before claiming its support.
- **Final answer and usage:** cover commentary before tools, the terminal answer, trailing notifications, successful empty output and empty error output. Across deliberate consecutive/resumed runs, assert actual native identity, correct final reply, no historical usage duplication, no summing cumulative reports, truthful partial/unavailable data and preserved valuation distinctions.
- **Supervision and recovery:** inject rejected cancellation, accepted cancellation with no terminal event, late cancellation, hung close, runner death and descendant execution. Assert bounded escalation, real termination/fencing evidence where available and protected recovery state when it is not. Exercise Worker disconnect/replacement and Sprout restart with no replay or unsafe lease release. Include supervised-process cases on macOS and Windows.
- **Execution policy and diagnostics:** prove the selected current host execution posture survives the replacement and concurrent sessions cannot change one another's process-global settings. Test instruction file preservation and useful bounded diagnostic/version reporting through Sprout-owned contracts. Verify that product records and Worker protocols do not depend on raw OAR records. Privacy-only scanner/projection tests are not required under ADR-0020.
- **#225 compatibility prototype:** use one origin-sensitive fixture contract for Pi, Codex and Claude through the proposed OAR route. Give local and work fixtures identical relative filenames with different contents, exercise read/edit/command or native patch behavior, and attempt forbidden host sentinel access. Evaluate exclusion/replacement/executor controls, remote MCP origin, binding change or required new-session behavior, resume and no local fallback. Record source-only, scripted, protocol-level and model-issued evidence separately. This bounded prototype does not substitute for #225's full authenticated remote-work, MCP and lifecycle acceptance.
- **Real production acceptance:** require bounded Codex and Pi model-issued runs through the enrolled Worker path on the supported macOS and Windows matrix. Demonstrate contract delivery, progress/final reply, continuation, interruption and recovery as well as truthful usage and selected host policy. A scripted contract pass or imported package alone does not certify a live runtime. Missing credentials or platform access is a named prerequisite, not a passing check.
- **Required checks:** run the repository's standard test and typecheck commands with explicit timeouts of at most 180 seconds, plus bounded live scenarios with compact evidence prepared under AGENTS.md repository/issue-tracker publishing hygiene. Reuse existing browser/service tests only where catalog/readiness/product behavior changes. Update-gate checks apply to the accepted runtime/platform scope; they do not claim support for every runtime shipped upstream.

## Out of Scope

- Implementing #225's Host-run execution mode, service argument, read-only Settings presentation, remote Environment operations Module, full MCP proxy, execution-location schema or full remote-work acceptance.
- Replacing Sprout admission, Task authority, leases, collaboration routing, Worker enrollment or recovery with OAR mechanisms.
- Exposing the complete OAR Session Interface, raw native RPCs or generic model-selected engine control to Core or Agents.
- OAR-managed child spawning, automatic parent delivery, native queueing as an alternate Agent wake path, or a separate scheduler.
- Pi Durable, checkpointed agent-loop execution, automatic unfinished-run continuation or tool replay.
- Universal engine compatibility, zero per-runtime acceptance, or automatic enablement of all discovered runtimes.
- Making agy, OpenCode, Cursor or other additional engines production gates for this minimal replacement.
- Removing currently working engines before their replacements pass acceptance.
- Engine installation/login through Web, centralized model credentials, credential transfer, or automatic native runtime upgrades.
- Repository mirroring, active Task movement, OS sandbox implementation for Host-run work, or claiming that a runner child process is a sandbox.
- A broad redesign of Web, financial reporting, storage or the Worker protocol unrelated to this replacement.

## Further Notes

- There is no open development map at the time of drafting. This is a feature specification; bounded research/prototype and production slices follow the existing development loop. An unresolved prerequisite does not become evidenced merely because the issue is labelled ready for an agent.
- Recommended order is: #225-oriented OAR compatibility prototype; evidenced substrate decision and minimal Codex/Pi Environment-hosted replacement; #225 implementation on the selected substrate; then broader runtime coverage. OAR is a proposed foundation choice, not an intrinsic technical prerequisite of #225.
- The inspected upstream package is OAR 0.35.0 at commit `8adde16fe2d12ae54af7d4dff86c3f224380a5c7`. The earlier integration plan inspected 0.28.0. Neither source inspection establishes production acceptance.
- Current OAR session options include MCP attachment but no standard members for Pi native tool replacement, Claude builtin-tool selection or Codex executor selection. The inspected Pi opener retains native tools and replaces bash only for an environment overlay; the inspected Codex opener configures cwd/MCP without remote executor selection. Configuration or extensions may resolve these gaps; that route must be verified rather than assumed impossible or complete.
- The current OAR Session contract promises bounded disposal of runtime processes and their descendants. Its embedded Pi Implementation nevertheless awaits native abort before a helper that bounds extension shutdown, and its prompt-and-wait helper waits without a further limit after an accepted cancellation. Host-level supervision remains necessary.
- Upstream Claude issue #55 was open during inspection and describes a background-task result incorrectly settling a pending prompt. Its presence is an explicit attribution prerequisite for that runtime, not a reason to invent a successful turn classification.
- This specification preserves the Cumora-derived engine seam, the Environment Worker placement and session-scope decisions, Task-held lease and Human lifecycle authority, enrollment-backed execution, non-inference readiness and truthful usage. OAR replaces vendor integration Implementation; it does not supply those product decisions.
