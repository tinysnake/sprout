## Problem Statement

Long-horizon work often passes between several Agents in one Working group (WG). If Agent 1 releases Environment A after its run and Agent 2 must acquire it later, unrelated work can acquire A in the gap. Agent 2 then cannot continue in the same working state, even though the handoff is intentional and the Environment is an essential part of that work.

The replacement execution model in #260 makes Tasks Project-owned records assigned to WGs, while Agent runs belong to conversations and Tasks acquire or release no Environment leases. Continuous occupancy therefore needs an explicit run-independent handoff mechanism. It must preserve unfinished work, validate successor authority, remain manageable when every work Environment is occupied, and avoid turning the Working group glance into an activity feed about who acquired each lease.

## Solution

Introduce **Lease escrow**: the current legitimate user deposits an Environment lease for an authorized successor without making the Environment available to unrelated work. The **Lease takeover scope** is either one WG or one specific Agent within that WG. Taking over transfers current use, preserves the same Environment reservation, and delivers a handoff note. The successor explicitly escrows again or releases normally; ending its run does not silently release an escrow-chain reservation.

The Working group glance shows all pending escrows and their handoff information to all current WG members, regardless of individual takeover eligibility. The server independently enforces eligibility. Once an escrow is taken over, it leaves the ordinary-member pending view; the glance does not disclose the successor or takeover history. The current user has its own work context, and the current WG owner and Human retain management visibility.

Escrow never releases automatically because of age. By default, 30 minutes without takeover requests owner adjudication, and an unresponsive Agent owner escalates to Human Attention 2 hours later. The owner can change takeover scope, arrange successor activation, release normally, or explicitly defer the next check. Human disbanding warns about all outstanding reservations and automatically cleans them up; failures remain blocking recovery under Human responsibility instead of silently becoming available.

## User Stories

1. As a working Agent, I want to escrow my Environment before handing work to another Agent, so that unrelated work cannot acquire it between runs.
2. As a working Agent, I want to name my WG as the takeover scope, so that any eligible current Agent member can continue the work.
3. As a working Agent, I want to name one Agent within my WG, so that only that intended successor can take over.
4. As a working Agent, I want escrow to validate my current use authority and membership, so that I cannot deposit someone else's lease or deposit into a WG I do not belong to.
5. As a working Agent, I want a named successor to have current WG membership and Environment permission, so that escrow cannot grant unauthorized access.
6. As a successor Agent, I want takeover to retain the original Environment, so that I continue from the existing Project workspace and working state.
7. As a successor Agent, I want a handoff note containing the continuation goal, current work state, and deliverable references, so that I understand what to do before operating the Environment.
8. As a Project participant, I want handoff context to exclude another Agent's private memory and raw reasoning, so that collaboration respects privacy.
9. As a successor Agent, I want to escrow again after my run, so that a third Agent can continue through the same protected handoff chain.
10. As a successor Agent, I want my run ending to leave an escrow-chain reservation occupied until an explicit disposition, so that unfinished work is not silently reassigned.
11. As a current lease user, I want to release normally when the chain is no longer needed, so that the Environment becomes available once release requirements are met.
12. As a WG member, I want the Working group glance to show every pending escrow, including those designated for another Agent, so that shared handoff information is available without personalized filtering.
13. As a WG member, I want to see the takeover scope and handoff information for a pending escrow, so that I understand what is waiting and who is eligible.
14. As a WG member, I want taken-over escrows to disappear from the glance without showing the successor or history, so that the glance avoids irrelevant activity noise.
15. As a current lease user, I want access to my own authorization and handoff context after takeover, so that hiding takeover activity does not obstruct my work.
16. As an eligible Agent, I want the server to validate scope and permissions at takeover, so that seeing a glance entry is never mistaken for permission to claim it.
17. As an eligible Agent competing for WG-wide escrow, I want exactly one concurrent takeover to succeed, so that two Agents cannot operate under independent exclusive rights.
18. As an Agent whose takeover loses a race, I want an explicit already-taken result, so that I can stop attempting work without acquiring a different Environment silently.
19. As an Agent retrying a request, I want duplicate requests to have one effective result, so that a retry cannot create another use right or repeat a handoff.
20. As a current lease user, I want stale requests from an earlier handoff to be refused or replayed without new effects, so that they cannot release or alter my newer reservation.
21. As a Human, I want old execution to be proven stopped before escrow becomes claimable, so that a handoff cannot introduce concurrent execution.
22. As a Human, I want the depositor's old operational authority revoked upon escrow, so that it cannot keep modifying the Environment after handing it off.
23. As a Human, I want membership and permission revocation to prevent later takeover without freeing the Environment, so that security changes do not lose unfinished work.
24. As a newly admitted authorized WG Agent, I want eligibility for WG-wide pending escrow, so that the current membership rather than a frozen member list determines who may help.
25. As a WG owner, I want notification when a named successor loses eligibility, so that I can designate another successor or reclaim the reservation.
26. As a WG owner, I want to inspect every outstanding escrow chain for my WG, so that I can manage resources even after pending items leave the ordinary-member view.
27. As a WG owner, I want to change a normal escrow's scope to another current member or the whole WG without releasing occupancy, so that I can resolve a stalled handoff safely.
28. As a WG owner, I want to arrange activation of eligible successors, so that a pending handoff can progress through an explicit coordination action.
29. As a WG owner, I want to reclaim normal escrow when no Agent is running and release requirements are satisfied, so that abandoned handoffs do not occupy resources forever.
30. As a Human, I want emergency release with unresolved stopping or cleanup evidence to remain Human-only, so that WG management does not bypass recovery authority.
31. As a Human, I want escrow management authority to follow the current WG owner rather than the historical creator, so that owner changes transfer current responsibility correctly.
32. As a former owner, I want current management permissions to be removed while historical actions stay attributable, so that ownership changes are effective without rewriting history.
33. As a working Agent, I want immediate successor activation to be optional, so that depositing a lease does not necessarily start another run.
34. As a working Agent requesting immediate activation, I want a named scope to wake the named Agent and a WG-wide scope to wake the owner, so that the system avoids broadcasting model work to every member.
35. As a WG owner, I want a pending escrow to request adjudication after a configurable interval, so that idle reservations receive attention without automatic eviction.
36. As an Agent WG owner, I want to adjudicate even when no work Environment is free, so that an occupied resource cannot prevent the decision that would release it.
37. As a Human WG owner, I want Human Attention instead of an Agent wake, so that the timeout reaches the actual responsible actor.
38. As a Human, I want unavailable or unresponsive Agent owners to escalate through a bounded process, so that a missed wake does not silently strand the reservation.
39. As a WG owner, I want to defer with a reason and a next check time, so that deliberate waiting is explicit rather than an indefinitely reset timer.
40. As a Human, I want scope changes, wake failures, repeated checks, and elapsed time never to release occupancy on their own, so that scheduling events cannot override work protection.
41. As a WG owner or Human, I want stale timeout attention to become obsolete after takeover or release, so that old reminders cannot affect newer work.
42. As a Human, I want a warning about pending and taken-over reservations when disbanding a WG, so that I understand the associated cleanup.
43. As a Human, I want disbanding to perform normal release automatically rather than require separate manual releases first, so that the management journey is direct.
44. As a Human, I want disbanding to stop related execution and prevent new work before freeing taken-over reservations, so that automatic cleanup cannot overlap with old work.
45. As a Human, I want WG disbanding to complete while failed cleanup becomes Human-owned recovery, so that a broken Worker does not trap WG management or silently free an unsafe Environment.
46. As a Human, I want Project workspace state retained on normal release, so that releasing coordination rights does not delete engineering results.
47. As a Human, I want core restart and Worker disconnection to retain escrow occupancy, so that service failures cannot make unfinished work available to unrelated Agents.
48. As a successor Agent, I want restored escrow to become claimable only after state agreement and absence of leftover execution are verified, so that restart recovery does not invent safe state.
49. As a WG owner, I want several independent escrowed Environments in one WG, so that editing and validation resources can be coordinated separately.
50. As a Human, I want all reservations to be inspectable without a WG count quota or automatic eviction, so that resource disposition stays explicit.
51. As a WG owner coordinating assigned Tasks, I want Task completion, cancellation, return, or reassignment not to release an Environment reservation automatically, so that Task records remain independent from conversation execution.
52. As a mobile or desktop Human operator, I want the same glance, management, disband warning, and recovery capabilities, so that device choice does not change control authority.

## Implementation Decisions

- **Execution boundary:** follow #260's Project-owned, WG-assigned Tasks and conversation-owned Agent runs. Tasks neither acquire nor release these leases. Use the current WG owner identity defined by #260; only Human manages owner changes. This feature does not recreate Task groups or Task-held lease lifecycle controls.
- **Module responsibilities:** extend Environment lease lifecycle and persistence, run admission and settlement, enrolled Worker execution authorization and recovery, conversation/WG governance, collaboration routing and Human Attention, authenticated Web/Agent actions, context assembly, and Working group glance/owner management projections. Place escrow lifecycle coordination behind one cohesive service boundary; callers must not independently sequence storage, Worker fencing, release, and notification.
- **Reservation model:** maintain durable exclusive occupancy across depositing, pending escrow, takeover, successor run settlement, repeated escrow, normal release, and recovery. Record the Project, Environment, capability, WG, current use identity when applicable, escrow episode/version, takeover scope, handoff note, timing, and attributable transitions. A WG governs eligibility and management but is not the lease owner. No native engine session or private Agent memory is transferred by this record.
- **Persistence and concurrency:** make the occupancy transition, episode advancement, and operational authority change atomic through existing transaction facilities. Use stable request identity and expected current episode/version or an equivalent concurrency contract. Persist enough information to replay a duplicate result without authorizing new work. A stale command, wake, timer, or release must not mutate a later episode.
- **Public action contract:** expose depositing with handoff/scope and optional immediate activation, takeover, explicit re-escrow, normal release, owner/Human scope change, owner/Human deferral with reason and next check, Working group glance queries, own-use queries, and privileged management queries. Authenticate the acting identity independently of request-supplied target identities. Return distinguishable unavailable/already-taken, unauthorized, stale-transition, and recovery-required outcomes with no partial grant on refusal.
- **Deposit eligibility:** only the current legitimate user may deposit, and it must be a current member of the target WG. A named successor must be a current Agent member. Both deposit and takeover enforce current Project membership and Environment permission. Scope binds stable identities; names and prior membership snapshots convey no authority.
- **Deposit ordering:** while stopping or confirming the old Environment execution, retain occupancy. Make escrow claimable only after stop proof is available and the former user's operational authority has been revoked. If stop proof is missing or execution outcome is uncertain, enter blocking Lease recovery rather than claimable escrow. An in-run deposit request must settle/revoke old work before allowing a successor to operate; recording an intention alone is not a completed deposit.
- **Takeover:** atomically transition one claimable escrow to exactly one current user and revalidate current scope, membership, permissions, WG lifecycle, and Environment readiness. Preserve the selected Environment and its working state; do not silently match another Environment on conflict. Ordinary run admission cannot steal pending escrow. Deliver handoff context before granting successor work.
- **Successor settlement:** a run using an escrow-chain reservation does not release occupancy merely by settling. Its user explicitly re-escrows or requests normal release. Unexpected holder/runner loss follows blocking recovery; no new episode becomes claimable without proof. Ordinary runs that never enter an escrow chain keep their separately defined settlement behavior.
- **Capability enforcement:** bound Environment operations borrow valid current execution authority. Escrow is an occupied reservation, not an executable Agent identity. A pending item, glance visibility, management access, or coordination activation does not authorize workspace operations. Revoke old operational authority at handoff and enforce the current generation at the Worker/operations boundary, including reads and mutations. Preserve existing enrolled Worker and connection-epoch fencing.
- **Handoff context:** require a durable note identifying continuation goal, current work state, and necessary deliverable references. Scope it to the Project/WG and provide it to the successor before work. Follow existing fact-form, bounded context and sanitization conventions; do not replay the depositor's private memory, raw tool transcript, or reasoning. Native session continuity remains Agent/engine/Environment scoped.
- **Glance visibility:** all current WG members see all pending escrows and pending handoff information, even if they lack takeover eligibility or a named scope selects another Agent. Enforce takeover separately. Taken-over items disappear from the ordinary-member pending view; do not project successor identity or takeover history into that glance or automatic ordinary-member activity notifications. The current user receives its own work information. Current owner and Human retain management history and outstanding-chain visibility. WG-external membership grants no access to this WG glance or handoff notes.
- **Owner authority:** the current owner and Human may modify a normal escrow's scope within its WG, with reason and before/after attribution, arrange activation, defer, or reclaim normally. Occupancy remains continuous during scope changes. A new owner inherits current management responsibility; the old creator/owner does not retain authority just because it deposited or created the WG. Preserve historical actors.
- **Authority limits:** owner reclamation applies to normal escrow with no active Agent run and satisfied normal-release requirements. Unknown stopping/cleanup evidence requires Human recovery handling; emergency Force Release remains Human-only, explicit, risk-acknowledged, and permanently attributable. Do not grant an Agent owner a risk-override release through a renamed endpoint or normal-disband cleanup.
- **Membership/permission changes:** loss of WG membership, Project membership, or Environment permission invalidates takeover but does not release occupancy or broaden a named scope. Notify the current owner to arrange a new successor or disposition. New eligible members can take WG-wide escrow. Revocation after takeover follows execution stopping/recovery controls and does not immediately reassign the Environment.
- **Normal release:** require old execution to be confirmed stopped and work to be preserved or subject to an explicit authorized disposition. Preserve the Project workspace. Release failure stays blocking and inspectable; it is never reported as free. Human-only emergency release may bypass unresolved proof only through the existing explicit emergency contract.
- **Activation:** deposit succeeds independently of optional immediate activation. A named scope targets its named Agent; a WG-wide scope targets the current owner to coordinate, or notifies a Human owner. Do not broadcast wake every member. Notification/admission failure remains attributable without releasing occupancy. Activation grants no takeover before successful authorization.
- **Timeout policy:** default owner adjudication at 30 minutes after successful deposit without takeover; for a responsive admission path but unanswered Agent owner, default Human escalation 2 hours after adjudication was requested. If the Agent owner cannot be awakened, escalate immediately; a Human owner receives Human Attention directly. Both intervals are configurable and timers survive restart. Scope changes and successor wakes do not reset timing. Explicit deferral records reason and next check time. No age-based release or automatic eviction exists.
- **Bounded routing:** use durable addressed coordination events/wake requests and Human Attention rather than inferred chat broadcasts. One unresolved timeout must not repeatedly admit owner runs. Deduplicate checks and delivery, resolve current owner at dispatch, and fence requests by escrow episode. Owner changes must not leave a historical owner with current adjudication authority. Takeover or release makes outstanding timeout action obsolete. Attention acknowledgement does not itself perform release or grant work authority.
- **No-free-Environment adjudication:** an Agent owner's coordination activation must be possible while all work Environments are occupied. Provide a restricted control-plane execution path for inspecting coordination facts, changing scope, arranging eligible wake, requesting normal release, and deferring. It must not acquire the escrowed work reservation, require a free work Environment, expose its working files, or fall back to privileged workspace operations. Reuse existing engine/runtime and no-lease coordination seams where possible; Worker-dependent cleanup may fail into Human recovery. If the owner cannot actually be activated, record the failure and escalate immediately rather than claiming adjudication occurred.
- **WG disband:** warn Human about both pending and taken-over outstanding escrow-chain reservations. On confirmed disband, close the WG to new takeover, re-escrow, and new chain runs, automatically attempt normal release of pending escrow, and stop related active execution before releasing taken-over reservations. Do not require prior manual release of each lease. Complete disband even if cleanup fails, with unclaimable blocking recovery transferred to Human. Disband confirmation is not emergency Force Release confirmation. Prevent stale deliveries from reopening work in the disbanded WG.
- **Restart and disconnection:** durable occupancy survives core loss or Worker disconnect. Re-enable takeover only after checking escrow/Worker state agreement and absence of leftover execution under current Worker authority. Otherwise retain blocking recovery and Human Attention. Already-taken execution follows the existing execution recovery contract; no timeout or reconnect silently frees it.
- **Multiple resources:** permit multiple independent escrow chains per WG. Each Environment has separate scope, handoff, timers, decisions, and recovery; no new count quota. Disband cleanup handles successful and failed releases independently while exposing every unresolved reservation to Human.
- **Scope and safety reconciliation:** update affected glossary, ADRs, API projections, prompts, and mobile/desktop journeys to distinguish pending visibility, current use, management authority, and emergency recovery. Preserve privacy, Project authority, Worker execution boundaries, truthful uncertainty, and existing startup execution-mode constraints. Lease-mode work in #258 must not weaken escrow's exclusive occupancy; shared read-lease escrow semantics are outside this feature.

## Testing Decisions

- **Primary seam:** test observable commands and queries through the composed authenticated application/API boundary, reusing the existing Web API harness and conversation/collaboration composition with real domain services. Use the same underlying lifecycle service for Agent actions and Human API controls. Avoid independent tests that merely mirror each internal method or stored field.
- **Good tests:** assert externally visible authority, Environment availability, working-state preservation, glance responses, successor context, and Attention outcomes. An implementation-preserving refactor should keep tests green. Each scenario must name a distinct safety or product regression; use parameterized variants instead of duplicating setup.
- **Continuity risk:** exercise Agent 1 deposit, an unrelated Agent's attempted acquisition during handoff, Agent 2 takeover and settlement, then re-escrow to Agent 3 and explicit release. Assert the same Environment/workspace is retained, occupancy never opens during the chain, and it becomes available only after normal release. Include Task mutation during the chain to prove execution independence.
- **Authority and race risk:** parameterize WG-wide versus named scope, current versus removed/unauthorized member, current versus former owner, and owner transfer. Race two eligible takeovers and race takeover against scope change or disband. Assert exactly one valid resulting use right, refusals without side effects, and no later mutation from stale or duplicate requests.
- **Operational fencing risk:** use existing Worker/operations integration support to attempt old-user reads and mutations after deposit and after a later takeover. Assert refusal and unchanged workspace. Missing stop proof must produce recovery, not a pending claimable glance entry. A ScriptedEngineAdapter alone is insufficient evidence for real Worker authorization fencing.
- **Projection/privacy risk:** query the Working group glance as a non-target current member and prove it includes named pending handoff information. After takeover, prove the ordinary-member projection and automatic glance activity do not expose successor identity/history. Prove own-use and owner/Human management remain usable and WG-external callers cannot retrieve handoff context or private Agent content.
- **Timeout/control-plane risk:** use an injected clock and controlled wake outcomes to cover 30-minute owner adjudication, 2-hour escalation, immediate unavailable-owner escalation, Human owner, explicit deferral, no reset on scope change/wake, and obsolete episode attention. With every work Environment occupied, prove owner coordination still executes without gaining workspace access. Repeated ticks/restart must not create repeated owner activations for the same unresolved timeout.
- **Disband/recovery risk:** exercise a WG with pending, taken-over/active, and failed-cleanup reservations. Assert warning facts, automatic cleanup without prior manual release, execution stop before availability, completed disband with failed entries still blocking under Human, and refusal of Agent emergency release. Preserve unresolved facts across explicit Human Force Release rather than presenting it as safe normal cleanup.
- **Real persistence risk:** supplement the primary seam with focused SQLite reopen tests using existing database transaction, lease-store, run-recovery, and enrollment/restart fixtures. Inject failures around deposit, takeover, notification, and disband cleanup commits. Reopen real storage and assert no free gap, no duplicate successor right, preserved handoff/timers/history, and correct recovery when Worker agreement is absent.
- **Prior art:** reuse existing authenticated Environment-router recovery tests, collaboration integration/routing and Human Attention tests, run admission/restart/continuation tests, Worker connection-epoch and operations authorization tests, and shared SQLite atomic-transition/reopen tests. Extend their established harnesses rather than introducing a second platform-wide test stack.
- **UI journey evidence:** add focused glance and management contract/component coverage plus one compact mobile/desktop end-to-end journey for pending visibility, eligible takeover, owner timeout disposition, and disband warning. Do not use broad snapshots or test internal component layout to prove authorization.
- **Verification:** production implementation must pass standard typecheck and meaningful regression checks through npm test with an explicit 180-second command timeout. If the default suite cannot finish under the known #254 bound, use documented disjoint bounded npm-test partitions covering all default-suite files, report counts/durations, and never count a timeout as a pass. This specification publication is not production test evidence.

## Out of Scope

- Implementing the full Task/WG replacement from #260 inside this feature, or rebuilding legacy Task groups, Task begin/end leases, validation, and run ownership.
- Cross-WG escrow transfers, automatic transfer of work to a different Environment, and native engine session sharing between Agents.
- Shared read-only escrow, new lease modes, copy-on-write, snapshots, per-file locks, and new workspace isolation engines.
- Agent-controlled WG membership, invitations, departure, disbanding, or owner transfer; these remain Human-managed under #260.
- Agent owner emergency release with unresolved evidence, including a Task-lead-style authority override applied to this feature.
- Automatic expiry release, count quotas, automatic eviction, Task polling, autonomous Task scheduling, and a general workflow engine.
- Ordinary-member takeover activity feeds, recipient-filtered glances, and publication of WG handoff details to WG-external members.
- Copying private Agent memory, raw reasoning, credentials, infrastructure secrets, or complete tool transcripts into shared handoff records.
- Multi-Human authorization expansion, deployment governance, and speculative adapter/platform breadth.

## Further Notes

- This specification synthesizes the Human's lease-escrow design interview and the explicit invocation to publish a spec; no additional product interview is required. Implementation design may choose concrete schema, endpoint names, and runtime wiring without changing these observable contracts.
- Pending escrow visibility is the escrow provider of the **Working group glance** (`docs/specs/working-group-glance.md`), which owns the shared query contract and membership-wide visibility rules used here.
- Related planning: #260, especially conversation execution #261 and replacement boundary #264. This is a production feature specification linked to that direction, not a silent expansion of #260's planning-only map or a claim that its baseline replacement is implemented. Consume the settled WG-owner/conversation-execution contract when integrating; do not preserve obsolete Task lease behavior to avoid integration work.
- **Conflict with #259:** this design explicitly replaces the assertion that a lease never spans runs for escrow chains, and does not adopt Task lead risk-override release into WG escrow management. Preserve #259's valid containing-lease requirement for bound operations and the attribution of uncertain outcomes. This specification does not rewrite, close, or accept #259, or change ordinary non-escrow run behavior by implication.
- **Relationship to #258:** read/read-write modes are separate work. Escrow promises retained exclusive occupancy; introducing concurrent readers must not silently allow unrelated use of an escrowed Environment. Shared-read escrow needs a separate decision and is not promised here.
- The pre-#260 Task-held lease and Task-group ADRs describe the legacy baseline. Update their affected claims during integration while retaining the Environment Worker boundary, Agent-private context/session boundaries, preserved Project workspace, and Human-only emergency release guarantees.
- Repository reference guidance identifies no mature Paperclip equivalent for Sprout's Environment lease model; its durable-workspace and work/execution separation principles remain useful prior art. No reference implementation or code adoption is claimed by this specification.
- Apply ready-for-agent. Keep this issue open until implementation and independent acceptance evidence demonstrate the specified behavior; publishing the specification alone does not evidence the feature.
