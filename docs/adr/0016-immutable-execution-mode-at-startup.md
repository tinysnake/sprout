# Sprout selects one immutable execution mode at startup

Ticket #225 retains Environment-hosted execution while adding Host-run placement. Ticket #240 completes the bounded Message-to-reply journey for Pi on the Sprout host; Ticket #249 adds Codex through the same Engine Interface and Runtime path. Both choices belong to one Sprout process and must be settled before that process accepts work. A browser setting, stored preference, or live mode switch could make Settings disagree with the Runtime graph and could admit work through a placement that was not active when authority was checked.

The Sprout service accepts `--execution-mode environment-hosted` or `--execution-mode host-run`. The argument is parsed before host configuration, Runtime construction, listeners, engine lookups, and remote operations. Omission selects `environment-hosted` on every boot. The resolved mode constructs one frozen execution strategy shared by run and Task admission. There is no second scheduler or hot-switchable graph. Pi Host-run remains available under its accepted readiness and isolation contract. Codex Host-run is available to development and conformance compositions through explicit adapter injection; the production Runtime keeps it unavailable while #248's named host-authority-exclusion prerequisite remains unresolved, even when `SPROUT_HOST_CODEX_MODEL` is set.

`environment-hosted` retains the existing Environment admission and execution journey. In `host-run`, a one-round Message run uses the Sprout-host Pi profile, or a development/conformance Codex profile, only after Project membership, exact configured model authority, supported effort, non-inference readiness, and isolation controls are established. Production composition does not create a Codex profile while its #248 prerequisite is unresolved. Host-run admission does not resolve an Environment, contact a Worker, or acquire a lease for an ordinary conversation. Its durable run record names `host-run` and the opaque Engine host profile. Its session key is partitioned by execution mode and host profile. Task admission remains tied to an Environment lease under ADR-0018.

The Host Pi profile uses its pinned SDK and explicitly registered provider; the Host Codex profile uses Codex CLI `0.159.3` through app-server JSON-RPC and Codex's experimental dynamic-tool protocol. Both profiles require explicit host model configuration, disable local built-in work tools and ambient discovery, and run behind the host isolation controls. The Codex sandbox permits reads from its private runner and configured Codex home, confines writes to those areas, and protects authentication/configuration files. Host-run workspace tools are typed and routed only to an explicitly selected remote Project workspace. Selecting one acquires an Orchestrator-owned `agent-run` lease before Worker contact; settled work releases it and uncertain work keeps it in Environment recovery. An ordinary conversation stays detached from a Work Environment and has no workspace catalog. The Codex app-server receives no native shell, plugin, browser, computer, code-mode, or ambient MCP tools. If installation, authentication, the exact authorized model, or any required isolation control is unavailable or unknown, the Message run is refused before engine acceptance. Sprout never substitutes an account, model, execution mode, or Environment. Selected Project MCP tools retain the approved Environment Worker's origin and use the containing run or Task lease; Sprout never launches their configured server.

Operator Settings reports the server's effective mode and non-inference readiness summaries for configured Host Pi and Host Codex profiles. When a Host Codex readiness step fails, Settings may display the failing allowlisted step and a bounded error category, without raw process/server text, paths, credentials, or endpoints. When production Codex composition is held by the unresolved #248 prerequisite, Settings reports the blocked state and its reason instead of implying that Codex is merely unconfigured. A Settings read may refresh local readiness observations for an available profile; it never performs a model turn or contacts an Environment Worker. Browser transport loss marks the displayed observation stale; reconnecting fetches a fresh authoritative snapshot. There is no mode write route, browser preference, or configuration watcher. The production Codex gate makes no host-authority-exclusion claim.

**Consequences**

- The Worker CLI does not choose the Sprout process mode. The normal service launcher forwards the argument to `src/main.ts`.
- Startup argument errors exit before host configuration is read and before any Runtime resource is constructed.
- Host readiness is scoped to the Sprout Engine profile and remains independent from Environment readiness. A Project's Environment access cannot authorize a host model or host filesystem access. The production Codex adapter factory is fail-closed until the #248 prerequisite is resolved; explicit model configuration alone does not enable it. Development conformance injects the pinned adapter through the existing Runtime seam.
- Host-run Messages keep the shared RunOrchestrator, Project membership checks, event streaming, reply projection, usage recording, and interruption lifecycle. Environment-hosted behavior remains unchanged. A selected remote workspace uses the Orchestrator's Agent-run lease; selected Project MCP uses the approved Worker's origin and containing run or Task lease. An uncertain remote operation protects its lease through Environment recovery.
- Tasks remain tied to a Work Environment under ADR-0018. A Host-run Task lead uses an available configured Host Pi profile, or an injected development/conformance Codex profile while the production gate is closed, and reuses the Task-held Environment lease for remote workspace and Project MCP operations; it does not create a second Task context or lease.
- A Settings read is a non-inference observation of the current process configuration. It may refresh local Host Pi or Host Codex readiness observations, but does not start a model turn, submit a run, or request an Environment Worker readiness probe.
- Placement work keeps the one Runtime admission seam and preserves Environment enrollment, Project authority, leases, and recovery guarantees. ADR-0017 records the selected mode and actual engine host/profile on admitted Runs and begun Tasks so a restart cannot silently relabel unfinished work.

**Rejected alternatives**

- Persisting the last selected mode would make omission depend on prior boots and could silently change placement after restart.
- Allowing Settings to switch mode would create a second authority path and require rebuilding or hot-switching the execution graph.
- Falling back from unavailable Host-run admission to Environment-hosted work would execute under a different placement than the Human selected.
- Reusing Environment readiness or Project Environment access for the Sprout-host engine would conflate Engine-host authority with work Environment authority.

**Reference**

`docs/references.md` was checked before implementation. AionUi's pinned ACP implementation at `dc78ccd8472e0787404d295bbd817e31f3133cf1` uses a single owner for its child process, protocol transport, pending requests, startup failure watch, and graceful shutdown, with a separate NDJSON adapter. Sprout follows that process-ownership pattern while keeping Codex app-server JSON-RPC and Sprout's Engine Interface. AionUi exposes ACP filesystem methods and injects MCP servers into local agents; Sprout instead sends only typed remote Workspace and approved Project MCP tools through the Environment Worker, because file authority and lease ownership stay with that Worker under ADR-0019 and #259. No reference code was copied. No reference establishes host-authority exclusion; the named #248 prerequisite remains open.
