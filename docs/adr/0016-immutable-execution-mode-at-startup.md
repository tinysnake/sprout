# Sprout selects one immutable execution mode at startup

Ticket #225 retains Environment-hosted execution while adding Host-run placement. Ticket #240 completes the bounded Message-to-reply journey for Pi on the Sprout host; Ticket #249 adds Codex through the same Engine Interface and Runtime path; Ticket #251 adds Claude Code through that shared seam. Each choice belongs to one Sprout process and must be settled before that process accepts work. A browser setting, stored preference, or live mode switch could make Settings disagree with the Runtime graph and could admit work through a placement that was not active when authority was checked.

The Sprout service accepts `--execution-mode environment-hosted` or `--execution-mode host-run`. The argument is parsed before host configuration, Runtime construction, listeners, engine lookups, and remote operations. Omission selects `environment-hosted` on every boot. The resolved mode constructs one frozen execution strategy shared by run and Task admission. There is no second scheduler or hot-switchable graph. Pi Host-run remains available under its accepted readiness and isolation contract. Codex Host-run remains unavailable in production while #248's named host-authority-exclusion prerequisite is unresolved. Claude Code Host-run uses the installed Claude Code CLI `2.1.294` and its native stream-JSON/MCP protocol; its model resolves from read-only user settings as `group/auto-mimo-v2-6-flash[1m]`, with configured effort `high`. This gateway alias currently maps to a non-Claude model; Sprout does not claim a Claude-native model. The configured model and effort must match these recorded values, and a changed authentication configuration is refused after readiness is accepted. The real model-issued scope and same-host enrolled Worker result are recorded in `docs/research/claude-host-run-conformance.md`.

Ticket #252's bounded composition evidence remains incomplete: the installed Pi `1.1.0` profile reported unknown readiness and the existing isolation probe requires `1.0.4`; Codex CLI `0.159.3` reported ready controls and an accepted dynamic catalog, but its completed model turn issued zero workspace or Project MCP calls; Claude Code CLI `2.1.294` completed the remote read/edit/stdio-MCP fixture and Worker traversal refusal, without exercising local Sprout-host read/write denial or no-fallback behavior. The exact scope evidence is in `docs/evidence/ticket-252-host-run-composition.md`; it does not waive #225's live-evidence requirement or #248's production Codex prerequisite.

`environment-hosted` retains the existing Environment admission and execution journey. In `host-run`, a one-round Message run uses an authorized Sprout-host Engine profile only after Project membership, exact configured model authority, supported effort, non-inference readiness, and isolation controls are established. Host-run admission does not resolve an Environment, contact a Worker, or acquire a lease for an ordinary conversation. Its durable run record names `host-run` and the opaque Engine host profile. Its session key is partitioned by execution mode and host profile. Task admission remains tied to an Environment lease under ADR-0018.

The Host Pi profile uses its pinned SDK and explicitly registered provider; the Host Codex profile uses Codex CLI `0.159.3` through app-server JSON-RPC and Codex's experimental dynamic-tool protocol. The Host Claude Code profile pins CLI `2.1.294` and the CLI's stream-JSON and stdio MCP protocol. It reads the exact authorized model and configured effort from the read-only user settings, projects those same values into isolated CLI settings without `--model` or `--effort` overrides, supplies authentication through a read-only helper, excludes built-in work tools, and checks the accepted initial catalog before processing a turn. Its non-inference readiness observes configuration and local isolation controls; it does not validate the configured token or reachability of the non-Claude model behind the alias. Raw process text, settings values beyond the exact authorized model, paths, credentials, and endpoints are never projected. All profiles route workspace and approved Project MCP operations through the shared Environment Operations and Worker authority. The Host-run Claude profile protects its user settings from writes and confines its own writes to runner/control roots. Selecting a remote workspace acquires an Orchestrator-owned `agent-run` lease before Worker contact; settled work releases it and uncertain work keeps it in Environment recovery. An ordinary conversation stays detached from a Work Environment and has no workspace catalog. If installation, authentication configuration, the exact authorized model, effort, or any required isolation control is unavailable or unknown, the Message run is refused before engine acceptance. Sprout never substitutes an account, model, execution mode, or Environment. Selected Project MCP tools retain the approved Environment Worker's origin and use the containing run or Task lease; Sprout never launches their configured server.

Operator Settings reports the server's effective mode and non-inference readiness summaries for configured Host Pi, Host Codex, and Host Claude Code profiles. Claude readiness reports the pinned CLI version, authentication-configuration presence, exact configured model/effort, and allowlisted probe failures; it does not claim that the gateway token or remote model endpoint was validated. A Settings read may refresh local readiness observations for an available profile; it never performs a model turn or contacts an Environment Worker. Browser transport loss marks the displayed observation stale; reconnecting fetches a fresh authoritative snapshot. There is no mode write route, browser preference, or configuration watcher.

**Consequences**

- The Worker CLI does not choose the Sprout process mode. The normal service launcher forwards the argument to `src/main.ts`.
- Startup argument errors exit before host configuration is read and before any Runtime resource is constructed.
- Host readiness is scoped to its Sprout Engine profile and remains independent from Environment readiness. A Project's Environment access cannot authorize a host model or host filesystem access. Claude Code's resolved model and effort are checked against the exact user-configuration values; its private in-memory configuration fingerprint prevents an account/config change after accepted readiness without retaining the credential or endpoint.
- Host-run Messages keep the shared RunOrchestrator, Project membership checks, event streaming, reply projection, usage recording, and interruption lifecycle. Environment-hosted behavior remains unchanged. A selected remote workspace uses the Orchestrator's Agent-run lease; selected Project MCP uses the approved Worker's origin and containing run or Task lease. An uncertain remote operation protects its lease through Environment recovery.
- Tasks remain tied to a Work Environment under ADR-0018. A Host-run Task uses the selected authorized Host Engine and reuses the Task-held Environment lease for remote workspace and Project MCP operations; it does not create a second Task context or lease.
- A Settings read is a non-inference observation of the current process configuration. It may refresh local Host Pi, Codex, or Claude Code readiness observations, but does not start a model turn, submit a run, or request an Environment Worker readiness probe.
- Placement work keeps the one Runtime admission seam and preserves Environment enrollment, Project authority, leases, and recovery guarantees. ADR-0017 records the selected mode and actual engine host/profile on admitted Runs and begun Tasks so a restart cannot silently relabel unfinished work.

**Rejected alternatives**

- Persisting the last selected mode would make omission depend on prior boots and could silently change placement after restart.
- Allowing Settings to switch mode would create a second authority path and require rebuilding or hot-switching the execution graph.
- Falling back from unavailable Host-run admission to Environment-hosted work would execute under a different placement than the Human selected.
- Reusing Environment readiness or Project Environment access for the Sprout-host engine would conflate Engine-host authority with work Environment authority.

**Reference**

`docs/references.md` was checked before implementation. AionUi's pinned ACP implementation at `dc78ccd8472e0787404d295bbd817e31f3133cf1` uses a single owner for its child process, protocol transport, pending requests, startup failure watch, and graceful shutdown, with a separate NDJSON adapter. Sprout follows that process-ownership pattern while keeping Claude Code CLI stream-JSON/MCP details within its adapter and the shared Sprout Engine Interface. AionUi exposes ACP filesystem methods and injects MCP servers into local agents; Sprout instead sends only typed remote Workspace and approved Project MCP tools through the Environment Worker, because file authority and lease ownership stay with that Worker under ADR-0019 and #259. No reference code was copied. The resolved model is the user-configured gateway alias `group/auto-mimo-v2-6-flash[1m]`; it is not represented as Claude-native. No reference establishes host-authority exclusion.
